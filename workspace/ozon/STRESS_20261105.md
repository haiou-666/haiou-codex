# Stress test — 300 product pages on one warmed jar (2026-11-05)

Single warmed session, sequential product-page requests through `composer-api.bx`.
Goal: find where the risk engine starts returning 403.

## Setup

| Item | Value |
|---|---|
| Warm-up | `AbtBatch` (Playwright) — challenge + settle, **23.9 s**, 9 cookies, `abt_data` 625 chars |
| Client | `curl_cffi` 0.17.0, `impersonate="chrome"`, HTTP/2, same proxy |
| Headers | `accept`, `accept-language`, `referer`, `sec-fetch-site/mode/dest` only |
| Target | `GET /api/composer-api.bx/page/json/v2?url=%2Fproduct%2F...` |
| Pool | 44 distinct product URLs harvested from category listing pages, cycled to 300 |
| Pacing | **none** — sequential, no sleep, no retries |

## Result

```
n=300   ok=300   fail=0   first_non200=null   codes={"200": 300}
request phase ~180 s  →  ~1.67 req/s
total wall 224.9 s (incl. 23.9 s warm-up + ~20 s harvest)
payload 51.9 MB total
```

**No 403 anywhere in 300 requests.** No challenge re-entry, no `fab_*` incident id,
no degradation at the tail.

## What this does and does not prove

**Proved:** at ~1.7 req/s sequential, a single warmed jar is not limited by request
count within 300 requests. There is no "N-th request gets 403" cliff in this range.
The earlier 403s were a **cold-jar** problem, not a volume problem.

**Not proved:**
- Only 44 distinct paths were cycled; a risk engine keying on path diversity or on
  per-URL visit counts would not be exercised here.
- Sequential only. Concurrency (e.g. 8 workers) is a different signal entirely.
- Time-based decay untested: the jar was used within ~4 min of minting. Whether it
  survives 1 h / 6 h idle is open.
- Cumulative volume >300 untested.

## Concurrency ladder (follow-up)

Same design as the sequential run — one warmed jar, its cookies copied verbatim into
N independent `curl_cffi` Sessions (server-side identity stays identical, no shared
Session object so no client-side races) — but `STRESS_W` worker threads.

| Workers | Requests | Wall | Throughput | p50 | p95 | max | 200s |
|---|---|---|---|---|---|---|---|
| 1 | 300 | 224.9 s | **1.67 req/s** | 0.54 s | 0.85 s | 3.35 s | 300/300 |
| 8 | 300 | 44.5 s | **6.75 req/s** | 0.89 s | 3.09 s | 4.17 s | 300/300 |
| 16 | 200 | 34.3 s | **5.83 req/s** | 1.47 s | 4.53 s | 10.97 s | 200/200 |
| 32 | 200 | 25.9 s | **7.73 req/s** | 3.19 s | 6.94 s | 10.78 s | 200/200 |

**No 403 at any width. Zero non-200 in 1000 requests total.** `first_non200` stayed `null`
in every run, and the 10-second buckets show no late-run degradation.

But look at the throughput column: it flattens at ~6–8 req/s while latency grows
monotonically with width. 8 workers → 6.75 rps, 16 workers → 5.83 rps (slower than 8!),
32 workers → 7.73 rps with p50 tripled to 3.19 s. That is a bandwidth ceiling, not a
server-side throttle: 165 KB × 7.7 rps ≈ **1.27 MB/s ≈ 10 Mbit/s**, which is what the
local proxy path sustains. Sequential mode only needed 0.29 MB/s, so it never touched
the wall.

The honest consequence: **this ladder never actually produced a high request rate.** The
real experiment for a rate-based throttle needs ~50–100 rps, which the current egress
cannot deliver. What it does establish:

- concurrency up to 32 sockets on one jar, over ~44 s, is fine on the wire;
- the 403s seen earlier came from cold jars, and nothing here reproduces them;
- at ~8 rps there is no per-cookie request-count trigger.

Reproduce: `STRESS_W=8 STRESS_N=300 python stress_conc.py` →
`stress/conc_results.jsonl` (per request, with wall-clock offset `t` and worker id `w`).
